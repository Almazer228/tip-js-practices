## 3. Реализация

### 3.1. HTTP-клиент

В модуле `api-client.js` реализован HTTP-клиент на основе Fetch API.

Поддерживаются методы GET, POST, PATCH и DELETE. Для POST и PATCH используется отправка JSON-тела с заголовком `Content-Type: application/json`.

Реализована обработка ответа 204 без попытки разбора JSON, установка заголовка Accept, тайм-аут запросов и отмена через AbortController.

Ошибки разделены на сетевые, HTTP-ошибки, тайм-ауты, отмену запроса и некорректные ответы сервера.

### 3.2. Доменный API

В модуле `task-api.js` реализованы операции:

- `getTasks()` — получение списка задач с фильтрами.
- `getTaskById()` — получение задачи по идентификатору.
- `getCategories()` — получение категорий.
- `loadInitialData()` — начальная загрузка задач и категорий.
- `createTask()` — создание задачи.
- `updateTask()` — редактирование задачи.
- `setTaskCompleted()` — изменение статуса задачи.
- `deleteTask()` — удаление задачи.
- `resetDemoData()` — восстановление исходных данных.

Перед передачей данных интерфейсу проверяется структура полученных задач и категорий.

### 3.3. Состояния интерфейса

В приложении реализованы четыре состояния списка:

- `loading` — выполняется загрузка данных.
- `ready` — задачи успешно загружены.
- `empty` — по выбранным фильтрам задач нет.
- `error` — произошла ошибка загрузки.

При ошибке пользователь может повторить запрос с помощью кнопки повтора.

### 3.4. Изменение данных

Реализованы создание задач, редактирование, смена статуса и удаление.

Перед отправкой формы выполняется проверка названия, приоритета и категории. После успешного изменения данные повторно запрашиваются с сервера, а список обновляется.

Во время выполнения операции кнопки блокируются, чтобы избежать повторной отправки запросов.

### 3.5. Защита от устаревшего ответа

Для отмены предыдущих запросов используется `AbortController`.

Дополнительно применяется счётчик запросов, который позволяет определить актуальность ответа. Благодаря этому результат более старого запроса не может перезаписать данные, полученные последним запросом.

Ошибки отменённых запросов не отображаются пользователю.

## 6. Ответы на контрольные вопросы

**1. Почему `fetch` не отклоняет Promise при ответе 404?**

Потому что Fetch API считает ответ 404 корректно полученным HTTP-ответом. Для определения ошибки необходимо самостоятельно проверить свойство `response.ok`.

**2. Почему ответ 204 нельзя разбирать вызовом `response.json()`?**

Потому что статус 204 означает, что сервер успешно выполнил запрос, но не вернул тело ответа. Поэтому JSON разбирать нечего.

**3. Чем состояние `empty` отличается от `error`?**

`empty` означает, что запрос выполнен успешно, но задач по заданным условиям нет. `error` означает, что получить данные не удалось из-за ошибки.

**4. Зачем отменять предыдущий запрос при смене фильтров?**

Чтобы не выполнять ненужные запросы и не позволять устаревшим ответам изменять актуальное состояние интерфейса.

**5. Почему после мутации список повторно запрашивается у API?**

Потому что сервер является источником данных. Повторный запрос позволяет получить актуальный список после создания, изменения или удаления задачи.
